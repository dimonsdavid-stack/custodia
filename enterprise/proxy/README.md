# Mesh ingress and credential rotation

`envoy.yaml` is a TLS1.3-only mutually authenticated attestation ingress. Envoy obtains rotating workload certificates and trust bundles directly from SPIRE SDS over a locally protected Unix socket. The ingress accepts only `spiffe://custodia.internal/workload/backend` and stays unusable if certificates or trust bundles are missing. Register the gateway and backend workload identities in SPIRE using node/workload selectors tied to the actual deployment, and mount `/run/spire/sockets/agent.sock` only into authorized proxies. Validate with the deployed Envoy binary's `--mode validate` before starting it.

SPIRE SDS workload keys are short-lived software-held TLS session identities. They are not represented as hardware-backed private keys. Hardware custody for the separate readiness assertion is supplied by the real external PKCS11 HSM provider in `hardware/src/main.rs`. A hardware-backed TLS private-key operation additionally requires an Envoy PrivateKeyProvider extension for the organization's actual HSM; SDS by itself does not provide HSM signing. This workspace does not include a fabricated HSM extension.

Limit this ingress at the VPC security-group/network-policy layer to the application workload. Configure SPIRE certificate TTL and rotation with the existing production identity authority. Bound connection/request counts with the included circuit breakers; maintain gateway process supervision with a fixed CPU/memory cgroup and a restart-on-failure policy. The gateway runs on loopback and performs no public HTTP exposure. The existing backend containment client uses Node's normal TLS connection; to cross this mTLS listener deploy an egress sidecar that presents the backend SPIFFE identity and routes the backend's HTTPS attestation hostname. Backend containment code is intentionally unchanged.
